# Knowledge-base RAG

RAG is exposed through the authenticated `/api/rag` endpoints and the standalone `/rag` frontend route. Uploaded PDF, Markdown, and TXT documents are indexed per authenticated user under `.rag-data/<userId>/index.json`; this store is separate from rewrite/paradigm data. Set `RAG_DATA_DIR` to move the local index directory. Batch uploads accept up to 100 files per request, with a 15 MB per-file and 60 MB aggregate limit.

RAG uses the Aliyun Bailian OpenAI-compatible embedding configuration: `ALIYUN_ACCESS_KEY`, `ALIYUN_ACCESS_BASE_URL`, and `ALIYUN_EMBEDDING_MODEL`. Optional settings are `ALIYUN_EMBEDDING_DIMENSIONS` (defaults to 768), `ALIYUN_EMBEDDING_BATCH_SIZE` (defaults to 8), and `ALIYUN_RERANK_MODEL` (defaults to `qwen3.7-text-rerank`). Reranking uses the compatible API's `/reranks` endpoint; without rerank credentials the service falls back to vector ranking.

## Accounts and private model settings

The app creates MySQL tables for accounts, hashed login sessions, encrypted per-user model settings, chat history, and image generations when the backend starts. The SQL definitions are also in `sql/schema.sql`.

Set `MODEL_CONFIG_ENCRYPTION_KEY` to a private Base64-encoded 32-byte key before users save their API keys. Generate one with a local secret manager or `openssl rand -base64 32`; do not commit it or change it after storing credentials unless you first re-encrypt those credentials. Users enter their own API key, base URL, text model, image model, and video model in the workspace settings. The key is encrypted at rest; the browser receives only its masked status. The settings panel can test a text-model request (which may incur a small charge). Passwords are scrypt-hashed, and the login cookie is HttpOnly, SameSite=Lax, and Secure in production.

Set `FRONTEND_ORIGIN` to the exact frontend origin (comma-separated if needed). Production deployments must use HTTPS and keep the encryption key in a secret manager. Existing anonymous records in the legacy `chat_sessions` tables are not assigned to new accounts; newly authenticated chat transcripts and image generations are kept in separate, user-owned tables.

For the admin console, set `ADMIN_EMAIL` and a unique `ADMIN_PASSWORD` (at least 14 characters) before the first backend startup. The first bootstrapped account is created only when `admin_accounts` is empty; subsequent administrators are added from `/admin`. Do not expose this bootstrap password in source control or public deployment logs.

## Observability

In production applications, observability is essential for understanding how your system behaves, detecting issues early, and maintaining reliable performance.

[NestJS Observe](https://observe.nestjs.com) automatically instruments your NestJS application, giving you deep visibility into your system with minimal setup:

- **Distributed tracing:** Follow requests across services and understand how they flow through your system.
- **Waterfall analysis:** Visualize request execution and identify slow operations, bottlenecks, and unexpected delays.
- **Performance analysis:** Analyze application performance in real time and quickly pinpoint areas that need optimization.
- **Metrics:** Track key application and infrastructure metrics to understand system health and performance trends.
- **Logging:** Centralize and correlate logs with traces and other telemetry to make debugging easier.
- **Error tracking:** Detect errors quickly and investigate their root causes with the surrounding context.
- **SLA monitoring:** Track service-level objectives and identify when your application is approaching or exceeding defined thresholds.
- **Alarms and alerts:** Set up alerts for critical errors, performance degradation, SLA violations, and other anomalies so your team can react quickly.
